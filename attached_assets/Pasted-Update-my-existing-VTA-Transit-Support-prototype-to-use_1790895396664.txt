Update my existing VTA Transit Support prototype to use two official public data sources:

1. 511 SF Bay Open Transit Data
   https://511.org/open-data/transit

2. Santa Clara Valley Transportation Authority Open Data
   https://data.vta.org/

IMPORTANT:
Do not rebuild or redesign the application.

Keep all existing features:
- resident report form
- English/Vietnamese interface
- speech input
- AI-generated contextual response
- persistent database
- History page
- existing styling
- synthetic-record labeling

The goal of this update is ONLY to connect the prototype to real public transit data and clearly show where every piece of information came from.

==================================================
1. 511 API AUTHENTICATION
==================================================

The 511 API key has already been added to Replit Secrets.

Use this environment variable:

SFBAY511_API_KEY

Read it only from the backend/server.

Example concept:

process.env["SFBAY511_API_KEY"]

or the equivalent for the application's current programming language.

NEVER:
- hardcode the API key
- place it in frontend JavaScript
- display it on the page
- print it in console logs
- save it in the database
- include it in API responses sent to the browser

If the secret is missing, show a developer-safe error without exposing credentials.

==================================================
2. IDENTIFY VTA IN 511
==================================================

Use the official 511 Operators API to determine the correct operator ID for Santa Clara Valley Transportation Authority.

Endpoint:

https://api.511.org/transit/operators

Use:
- api_key from SFBAY511_API_KEY
- format=json when supported

Do not guess the VTA operator ID.

After identifying it, cache the operator information so the application does not repeatedly request it.

==================================================
3. 511 STATIC TRANSIT INFORMATION
==================================================

Use the official 511 APIs to match the route and stop entered by the resident.

Use:

LINES API
https://api.511.org/transit/lines

STOPS API
https://api.511.org/transit/stops

Use these to identify:
- route number/name
- official route ID
- stop name
- stop ID / stop code
- stop location when available

If multiple stops have similar names, do not silently guess.

If possible, show the user a small list of matching stops or ask them to be more specific.

Do not add a complicated trip-planning interface.

==================================================
4. LIVE 511 STOP INFORMATION
==================================================

Use the official 511 Stop Monitoring API:

https://api.511.org/transit/StopMonitoring

Use:
- api_key
- agency
- stopcode when known
- format=json

Use this endpoint for current expected arrivals and departures.

Only display information that actually exists in the returned API response.

For example:

"Live 511 data currently shows the next expected Route 22 arrival in approximately 8 minutes."

The 8-minute value MUST come from the API response.

Never invent:
- arrival times
- departure times
- canceled trips
- vehicle locations
- delays

==================================================
5. 511 SERVICE ALERTS
==================================================

Use the official Service Alerts endpoint:

https://api.511.org/transit/servicealerts

Use:
- api_key
- agency
- format=json

Check whether an active alert appears relevant to the user's:
- route
- stop
- reported issue

If an alert is found, summarize it accurately.

Example:

"511 currently lists an active service alert affecting this route."

If no matching alert is found, say:

"No matching active service alert was found in the available 511 data."

Do NOT turn that into:

"There is no delay."

A bus may be delayed without a service alert.

==================================================
6. VTA OPEN DATA
==================================================

Also connect the prototype to:

https://data.vta.org/

Treat this as an official VTA public-data source.

First inspect the VTA Open Data catalog and identify a real, machine-readable dataset that is directly relevant to this prototype.

Prefer a dataset related to:
- transit stops
- transit routes
- transit facilities
- service information
- accessibility
- other information directly relevant to the resident's transit report

IMPORTANT:

Do not invent:
- dataset names
- dataset IDs
- API endpoints
- file URLs
- column names

Only use a VTA dataset if it actually exists on data.vta.org.

If the portal provides a CSV, JSON, GeoJSON, REST API, downloadable file, or another machine-readable resource, use that official resource.

Store metadata about the dataset:

- exact dataset title
- publisher: Santa Clara Valley Transportation Authority
- original source URL
- resource/download URL
- date retrieved

Use VTA Open Data primarily as official reference/context data.

Use 511 as the primary source for real-time arrivals and service alerts.

Do not pretend that static VTA Open Data is real-time unless the actual dataset explicitly says that it is.

==================================================
8. RESPONSE WORKFLOW
==================================================

When a resident submits a report:

STEP A
Save the resident's complete report.

STEP B
Identify the general issue type, such as:

- Service Reliability
- Missed Connection
- Accessibility
- Stop/Facility Issue
- Safety Concern
- Information/Signage
- Other Transit Issue

STEP C
Check whether the resident supplied a route and/or stop.

STEP D
Use official route and stop information to verify the location when possible.

STEP E
If enough information exists, query 511 Stop Monitoring.

STEP F
Query relevant 511 Service Alerts.

STEP G
Use relevant VTA Open Data when it provides useful supporting context.

STEP H
Generate a short response using ONLY:

1. information reported by the resident
2. real information returned by 511
3. verified information from VTA Open Data

Do not allow the AI to invent missing facts.

No matching active service alert was found for this route, so this prototype cannot confirm why the bus is delayed."

IMPORTANT:

"8 minutes" is only an example.

The actual application must replace that with the real value returned by the API.

18. FAILURE HANDLING
==================================================

If the 511 API fails:

"Your report was saved, but live 511 transit information could not be retrieved at this time."

If route/stop information is missing:

"Your report was saved. A route and stop are needed to check live arrival information."

If the route cannot be matched:

"Your report was saved, but the route could not be matched to the available transit data."

If the stop cannot be matched:

"Your report was saved, but the stop could not be matched to the available transit data."

If VTA Open Data cannot be reached:

Continue using 511 if it is available.

Do not fail the entire submission because the secondary VTA Open Data source is unavailable.
